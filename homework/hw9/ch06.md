# 第 6 章　讓 LLM 使用工具（下）原生版

## 【本章重點】

第 5 章靠 prompt「拜託」模型照格式寫紙條；這一章改用 Gemini API **內建的工具呼叫（function calling）**：用 **JSON Schema** 把工具的名稱、說明、參數型別交給 API，模型就會回傳**專用格式**的工具請求，不用再自己解析 JSON。
**核心觀念完全沒變**：模型還是只會「說」要用哪個工具，真正執行的還是你的程式，結果還是要送回給模型。改變的只是「紙條的格式」從自訂的文字，變成 API 定義好的欄位。
原生版更可靠、prompt 更短，還能一次要求好幾個工具（平行呼叫）。

---

## 【為什麼需要這一章】

第 5 章的手刻版雖然能動，但 5.7 節列出了好幾個問題，其中跟「格式」有關的是：

| 手刻版的問題 | 實際會遇到的狀況 |
|-------------|----------------|
| 格式常出錯 | 模型加了 `` ```json ``、多講一句話、漏了 `args`，全靠 `parse_json_reply()` 救 |
| prompt 越寫越長 | 每多一個工具，`TOOL_PROMPT` 就要多一段說明；10 個工具就是一大篇 |
| 參數寫錯 | 模型把 `day` 寫成 `date`，或傳 `"明天"` 給 `get_schedule` |
| 工具結果偽裝成使用者的話 | `[工具結果]` 用 `user` 角色送回，模型分不清「使用者說的」和「程式查到的」 |

這些問題有一個共同的根源：**模型和程式之間的「紙條格式」是我們自己發明的，模型只能憑 prompt 去猜。**

既然所有人都需要工具呼叫，模型廠商乾脆把它做成 API 的正式功能，並且**專門訓練模型**照這個格式輸出。這一章就來使用這個功能。

## 【觀念解說】

### 6.1 為什麼 API 要內建工具呼叫

**比喻：手寫紙條 vs 公司的正式申請單。**

- 手刻版像是顧問**隨手寫紙條**給助理：「幫我查一下星期五課表～」。字跡潦草、格式每次不同，助理常看不懂。
- 原生版像是公司印好的**正式申請單**：「申請項目：□查課表　日期：＿＿（只能填星期一～星期日）」。欄位固定、選項有限制，而且顧問**受過專門訓練**，知道怎麼填這張單子。

**回到技術說明，原生工具呼叫改變了三件事：**

```text
                      手刻版（第 5 章）                原生版（本章）
  ─────────────────────────────────────────────────────────────────────
  告訴模型有哪些工具    寫在 system prompt 的文字裡       放在 API 的 tools 欄位（JSON Schema）
  模型的紙條            一段文字，要自己解析 JSON          回應裡的專用欄位 function_call
  送回工具結果          偽裝成 user 訊息「[工具結果]」     專用欄位 function_response
```

而**沒有改變**的是：

```text
  模型說要用工具  →  你的程式執行  →  結果送回模型  →  模型回答
```

### 6.2 用 JSON Schema 描述工具

**JSON Schema（JSON 結構描述）**：一種「用 JSON 來描述 JSON 長什麼樣子」的標準寫法。例如：「這個物件要有一個叫 `day` 的欄位，型別是字串，只能是星期一～星期日其中之一，而且一定要填」。

**工具宣告（function declaration）**：用 JSON Schema 寫成的「工具說明書」，包含三個部分：

```json
{
  "name": "get_schedule",
  "description": "查詢某一天的課表。",
  "parameters": {
    "type": "object",
    "properties": {
      "day": {
        "type": "string",
        "enum": ["星期一", "星期二", "星期三", "星期四", "星期五", "星期六", "星期日"],
        "description": "要查詢的星期幾"
      }
    },
    "required": ["day"]
  }
}
```

| 欄位 | 意思 | 給誰看 |
|------|------|-------|
| `name` | 工具名稱，要和 `TOOLS` 的 key 一模一樣 | 模型和你的程式 |
| `description` | 工具做什麼、什麼時候該用 | **模型**（它靠這段文字決定要不要用這個工具） |
| `parameters` | 參數的結構 | 模型 |
| └ `type: "object"` | 參數整體是一個物件（dict） | |
| └ `properties` | 每個參數的名稱、型別、說明 | |
| └ `enum` | **只能從這幾個值裡面選** | |
| └ `required` | 哪些參數一定要給 | |

注意 `enum`：第 5 章模型可能傳 `"明天"` 給 `get_schedule`，害程式當掉。現在 schema 直接規定「只能是星期一～星期日」，模型就知道不能填「明天」，只能先去查時間。

`description` 寫得好不好，直接影響模型會不會在對的時機用對的工具。第 5 章 `TOOL_PROMPT` 裡的提醒（「不知道今天星期幾時先用 get_current_time」「算數一律用 calculator」），現在改寫進各工具的 `description` 裡。

### 6.3 送出工具定義

在 REST API 裡，工具宣告放在請求的 `tools` 欄位：

```json
{
  "system_instruction": {"parts": [{"text": "你是金門大學校園小助理……"}]},
  "contents": [
    {"role": "user", "parts": [{"text": "星期五有什麼課？"}]}
  ],
  "tools": [
    {
      "functionDeclarations": [
        {"name": "calculator", "description": "...", "parameters": {...}},
        {"name": "get_current_time", "description": "..."},
        {"name": "get_schedule", "description": "...", "parameters": {...}},
        {"name": "get_weather", "description": "...", "parameters": {...}}
      ]
    }
  ]
}
```

用 Python SDK 時，則是放在設定裡：

```python
config=types.GenerateContentConfig(
    system_instruction=SYSTEM_PROMPT,
    tools=[types.Tool(function_declarations=TOOL_DECLARATIONS)],
)
```

`TOOL_DECLARATIONS` 是一個 list，裝著四個工具宣告（程式 6-1）。

> **工具定義每次都要送。** 還記得第 3 章的「無狀態」嗎？API 不會記得你上次給過哪些工具，所以**每一次**呼叫都要把 `tools` 一起送出去。這些說明也會佔用輸入 token。

### 6.4 讀懂模型回傳的 `function_call`

模型想用工具時，回應的 `parts` 裡不會是 `text`，而是 `functionCall`：

```json
{
  "candidates": [
    {
      "content": {
        "role": "model",
        "parts": [
          {
            "functionCall": {
              "name": "get_schedule",
              "args": {"day": "星期五"}
            },
            "thoughtSignature": "CiQB0e2Kb7...（一長串編碼）"
          }
        ]
      },
      "finishReason": "STOP"
    }
  ]
}
```

- `functionCall.name`：要用哪個工具。
- `functionCall.args`：參數，**已經是 JSON 物件**，SDK 會轉成 Python dict，不用再 `json.loads()`。
- `thoughtSignature`（思考簽章）：新一代 Gemini 模型在呼叫工具時，會附上一段加密過的資料，記錄它「為什麼決定用這個工具」的推理過程。**下一次呼叫時必須原封不動送回去**，否則模型可能接不上，甚至回傳錯誤。

在 Python SDK 裡，可以用 `response.function_calls` 直接拿到所有工具請求：

```python
for call in response.function_calls:
    print(call.name, call.args)     # get_schedule {'day': '星期五'}
```

### 6.5 送回 `function_response`

工具執行完，要用 `functionResponse` 格式送回去：

```json
{
  "role": "user",
  "parts": [
    {
      "functionResponse": {
        "name": "get_schedule",
        "response": {"result": "{\"day\": \"星期五\", \"courses\": [...]}"}
      }
    }
  ]
}
```

- 這則訊息的 role 雖然還是 `user`，但內容是 `functionResponse` 這種**專用的部分（part）**，模型很清楚這是「工具結果」，不會跟使用者說的話搞混。
- `response` 必須是一個物件（dict）。我們把 `run_tool()` 回傳的字串放在 `result` 欄位裡。

**完整的對話紀錄變化（和第 5 章 5.6 節對照）：**

```text
  [system]   SYSTEM_PROMPT（不需要 TOOL_PROMPT 了！工具說明在 tools 欄位）
  [user]     星期五有什麼課？
                        ── 第 1 次呼叫 LLM（附上 tools）──
  [model]    functionCall: get_schedule(day="星期五")  ＋ thoughtSignature
                        ── 程式執行 get_schedule(day="星期五") ──
  [user]     functionResponse: get_schedule → {"day": "星期五", ...}
                        ── 第 2 次呼叫 LLM（附上 tools）──
  [model]    text: 「星期五你在 09:10 有程式設計實習。」
```

### 6.6 在通用格式裡記錄工具呼叫

本書的程式一直使用**通用格式**的 `messages`（`role` ＋ `content`），由 `call_llm()` 負責轉成 Gemini 格式。為了支援原生工具呼叫，我們在通用格式裡加上兩種訊息：

```python
# 模型要求使用工具（紙條）
{"role": "assistant", "content": "", "tool_calls": [{"name": "get_schedule", "args": {"day": "星期五"}}], "raw": ...}

# 工具的執行結果
{"role": "tool", "name": "get_schedule", "content": "{\"day\": \"星期五\", ...}"}
```

| 欄位 | 用途 |
|------|------|
| `tool_calls` | 模型要求的工具清單（可能不只一個） |
| `raw` | Gemini 回傳的**原始內容**，裡面有思考簽章；送回時直接使用它，不要自己重建 |
| `role: "tool"` | 新角色，代表「工具的執行結果」，轉換時會變成 `functionResponse` |

> 這個寫法和 OpenAI 等其他家 API 的格式很像（它們也有 `tool_calls` 和 `tool` 角色）。第 11 章會看到，很多框架也是用類似的「通用格式」來支援不同廠商的模型。

負責轉換的是新函式 `call_llm_tools(messages)`。它跟 `call_llm()` 的差別：

| | `call_llm()` | `call_llm_tools()` |
|---|---|---|
| 送出 | messages | messages ＋ `TOOL_DECLARATIONS` |
| 看得懂的角色 | system / user / assistant | 再加上 assistant 的 `tool_calls` 和 `tool` |
| 回傳 | 字串 | dict：`{"text": ..., "tool_calls": [...], "raw": ...}` |

### 6.7 手刻版 vs 原生版：逐項對照

| 項目 | 手刻版（第 5 章） | 原生版（本章） |
|------|-----------------|---------------|
| 工具說明放哪裡 | `TOOL_PROMPT`（system prompt 裡的文字） | `TOOL_DECLARATIONS`（API 的 `tools` 欄位） |
| 說明的寫法 | 自然語言＋範例 | JSON Schema（型別、enum、required） |
| 模型的紙條 | 文字 `{"tool": ..., "args": ...}` | 專用欄位 `function_call` |
| 解析紙條 | `parse_json_reply()`，可能失敗 | SDK 直接給 `name` 和 `args` dict |
| 判斷「要用工具」還是「回答」 | 看 JSON 裡有 `tool` 還是 `answer` | 看有沒有 `function_call` |
| 最終回答 | 也要包成 `{"answer": ...}` | 直接是普通文字 |
| 工具結果的角色 | 偽裝成 `user`，加上 `[工具結果]` | 專用的 `function_response` |
| 參數限制 | 只能在 prompt 裡拜託 | `enum`、`required` 寫進 schema |
| 一次用幾個工具 | 一個 | 可以好幾個（平行呼叫） |
| 換別家 API | prompt 照用 | 格式要改（各家欄位名稱不同） |
| 誰執行工具 | **你的程式** | **你的程式**（完全一樣！） |

最後一列最重要：**原生版並沒有讓模型「真的會執行」工具。** API 只是幫你把紙條的格式標準化，執行和送回結果，還是你的程式的工作。

### 6.8 一次叫多個工具（平行呼叫）

**平行函式呼叫（parallel function calling）**：模型在**一次回應**中，要求同時使用好幾個工具。

例如問「金門和台北今天的天氣如何？」，模型可能一次回傳兩個 `function_call`：

```text
  [model]  functionCall: get_weather(city="金門")
           functionCall: get_weather(city="台北")      ← 同一則回應裡的兩張紙條
                    ── 程式依序執行兩個工具 ──
  [user]   functionResponse: get_weather → 金門的天氣
           functionResponse: get_weather → 台北的天氣  ← 結果也放在同一則訊息裡送回
```

這兩個工具**互不相關**（查金門不需要等台北的結果），所以可以一起要求。但「明天有什麼課？」就不行：要先知道今天星期幾，才能決定查哪一天的課表，這種**有先後順序**的工具呼叫，還是需要第 7 章的迴圈。

> 「平行」指的是模型「一次要求多個」，你的程式可以依序執行，也可以真的同時執行。本書為了簡單，用 for 迴圈依序執行。

```python
def calculator(expression):
    """計算數學算式，例如 "(3 + 4) * 2"。只允許數字和 + - * / ( ) ."""
    allowed = set("0123456789+-*/(). ")
    if not set(expression) <= allowed:
        return "錯誤：算式只能包含數字和 + - * / ( ) ."
    if "**" in expression:
        return "錯誤：不支援次方運算"
    return eval(expression, {"__builtins__": {}}, {})


def get_current_time():
    """取得台灣現在的日期、星期與時間"""
    now = datetime.now(ZoneInfo("Asia/Taipei"))
    weekday = WEEKDAYS[now.weekday()]
    return f"{now.strftime('%Y-%m-%d')} {weekday} {now.strftime('%H:%M')}"

    """查詢某一天的課表，day 必須是「星期一」～「星期日」"""
    if day not in FAKE_SCHEDULE:
        raise ValueError(f"day 必須是星期一到星期日，收到的是：{day}")
    return {"day": day, "courses": FAKE_SCHEDULE[day]}


def get_weather(city):
    """查詢某個城市今天和明天的天氣"""

        return {"city": city, "error": "沒有這個城市的天氣資料"}

    result = func(**args)
    if isinstance(result, str):
        return result
    return json.dumps(result, ensure_ascii=False)
```

**逐段解說：**

### 程式 6-3：`call_llm_tools()` —— 原生版的 `call_llm`

這段定義函式本身**不需要 API key**，但最後的測試需要（沒有 API key 的讀者請跳過最後的測試部分）。

```python
def call_llm_tools(messages, temperature=None, max_output_tokens=1024):
    """
    原生工具呼叫版的 call_llm：把通用格式的 messages 連同工具宣告一起送給 Gemini。
    回傳 dict：{"text": 文字回答, "tool_calls": [{"name": ..., "args": {...}}], "raw": 模型的原始回應內容}
    """
    system_text = None
    contents = []

    # ===== 把通用格式轉成 Gemini 的格式 =====
    for msg in messages:
        if msg["role"] == "system":
            system_text = msg["content"]

        elif msg["role"] == "user":
            contents.append(types.Content(role="user", parts=[types.Part.from_text(text=msg["content"])]))

        elif msg["role"] == "assistant":
            if msg.get("raw") is not None:
                # 有原始內容就直接用，才不會弄丟思考簽章
                contents.append(msg["raw"])
            else:
                # 沒有原始內容（例如對話是 mock 產生的），就自己組
                parts = []
                if msg.get("content"):
                    parts.append(types.Part.from_text(text=msg["content"]))
                for call in msg.get("tool_calls", []):
                    parts.append(types.Part(function_call=types.FunctionCall(name=call["name"], args=call["args"])))
                contents.append(types.Content(role="model", parts=parts))

        elif msg["role"] == "tool":
            # 工具結果要包成 function_response
            part = types.Part.from_function_response(name=msg["name"], response={"result": msg["content"]})
            # 連續的工具結果（平行呼叫）要放在同一則訊息裡
            last = contents[-1] if contents else None
            if last is not None and last.role == "user" and last.parts[0].function_response is not None:
                last.parts.append(part)
            else:
                contents.append(types.Content(role="user", parts=[part]))

    # ===== 呼叫 API，附上工具宣告 =====
    response = client.models.generate_content(
        model=MODEL_NAME,
        contents=contents,
        config=types.GenerateContentConfig(
            system_instruction=system_text,
            temperature=temperature,
            max_output_tokens=max_output_tokens,
            tools=[types.Tool(function_declarations=TOOL_DECLARATIONS)],
        ),
    )

    # ===== 整理回應：分出文字和工具請求 =====
    content = response.candidates[0].content
    text = ""
    tool_calls = []
    if content is not None and content.parts:
        for part in content.parts:
            if part.function_call is not None:
                tool_calls.append({"name": part.function_call.name, "args": dict(part.function_call.args or {})})
            elif part.text and not part.thought:
                text += part.text

    return {"text": text, "tool_calls": tool_calls, "raw": content}


# 測試
result = call_llm_tools([
    {"role": "system", "content": SYSTEM_PROMPT},
    {"role": "user", "content": "星期五有什麼課？"},
], temperature=0)
print("文字：", repr(result["text"]))
print("工具請求：", result["tool_calls"])
```

**逐段解說：**

- **整體結構**和第 2 章的 `call_llm()` 一樣分三段：轉換格式 → 呼叫 API → 整理回應。這次改用 SDK 的 `types.Content`、`types.Part` 物件來組，因為工具呼叫的 part 比純文字複雜。
- **`user` 訊息**：`types.Part.from_text(text=...)` 建立一個文字 part，再包進 `types.Content(role="user", ...)`。效果和第 2 章的 `{"role": "user", "parts": [{"text": ...}]}` 一樣。
- **`assistant` 訊息**：
  - 有 `raw` 就**直接放回去**，這樣思考簽章會完整保留（6.4 節）。
  - 沒有 `raw` 時（例如 mock 產生的紀錄），自己用 `types.FunctionCall` 組出工具請求。
- **`tool` 訊息**：
  - `types.Part.from_function_response(name=..., response={"result": ...})`：建立 6.5 節的 `functionResponse`。`response` 必須是 dict，所以把字串放在 `result` 裡。
  - **合併連續的工具結果**：如果上一則訊息也是工具結果，就把這個 part 加進同一則（`last.parts.append(part)`），而不是新增一則。這是 6.8 節平行呼叫需要的。
- **呼叫 API**：和程式 6-2 一樣，加上 `tools`。
- **整理回應**：
  - 一一檢查回應的每個 part：有 `function_call` 就加進 `tool_calls`；是文字就接到 `text`。
  - `part.thought`：如果模型有開啟「顯示思考內容」，思考的文字也會是 part，這裡把它排除，只留正式回答。
  - `dict(part.function_call.args or {})`：確保參數一定是普通的 dict（沒參數時是空 dict）。
  - 回傳的 `raw` 就是模型原始的 `content`，呼叫端要把它存進 assistant 訊息裡。

**預期輸出：**

```text
文字： ''
工具請求： [{'name': 'get_schedule', 'args': {'day': '星期五'}}]
```

文字是空的，因為模型這次只寫了紙條，還沒有要回答。

### 程式 6-4：完成一次原生工具呼叫 —— `ask_with_native_tools()`

這段使用 `llm_tools()`：有 API key 時它是 `call_llm_tools`，沒有的話是程式 6-5 的 `mock_llm_tools`。

```python

def ask_with_native_tools(user_input):
    """原生版工具呼叫：最多進行一輪工具呼叫（這一輪可以同時用好幾個工具），然後回答"""
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},   # 不需要 TOOL_PROMPT 了
        {"role": "user", "content": user_input},

    if not response["tool_calls"]:
        return response["text"]

    # 把模型的紙條（含原始內容）記進對話
    messages.append({
        "role": "assistant",
        "content": response["text"],
        "tool_calls": response["tool_calls"],
        "raw": response["raw"],
    })

    # 一張一張執行紙條上的工具，結果用 tool 角色記進對話
    for call in response["tool_calls"]:
        result = run_tool(call["name"], call["args"])
        print(f"  [程式執行] {call['name']}({call['args']}) → {result}")

    response = llm_tools(messages, temperature=0)
    if response["tool_calls"]:
        names = [c["name"] for c in response["tool_calls"]]
        return f"（模型還想再使用 {names}，但這個函式只支援一輪工具呼叫）"
    return response["text"]
```

**逐段解說：**

- **messages 的 system**：只有 `SYSTEM_PROMPT`。和第 5 章比，少了一大段 `TOOL_PROMPT`。
- **判斷要不要用工具**：`if not response["tool_calls"]`，沒有工具請求就直接回傳文字。不用再檢查 `"answer" in action`，也不用 `parse_json_reply()`。

## 【常見錯誤】

| 錯誤情況 | 原因 | 解決方式 |
|---------|------|---------|
| 以為原生版是「模型自己執行工具」 | 誤解 | 執行的永遠是你的 `run_tool()`，API 只是把紙條格式標準化 |
| `400`，訊息提到 `properties: should be non-empty` | 沒有參數的工具寫了空的 `properties` | 沒有參數就整個省略 `parameters` |
| 模型要求的工具 `run_tool()` 找不到 | `TOOL_DECLARATIONS` 的 `name` 和 `TOOLS` 的 key 不一致 | 用程式 6-1 最後的檢查確認名稱一致 |
| 第 2 次呼叫出現錯誤，提到 signature | 自己重建了模型的工具請求，弄丟思考簽章 | 把 `response["raw"]` 存進 assistant 訊息，原封不動送回 |
| 第 2 次呼叫時模型好像不知道工具結果 | 忘了把 assistant 的紙條加進 messages，只加了 tool 結果 | 一定要依序加入：assistant（含 `tool_calls`）→ tool 結果 |
| `TypeError: 'NoneType' object is not iterable` | `response.function_calls` 在沒有工具請求時是 `None` | 寫成 `response.function_calls or []` |
| SDK 印出警告：there are non-text parts in the response | 回應裡有 `function_call` 時還用 `response.text` | 自己逐一檢查 part（參考 `call_llm_tools()`） |
| 模型沒有用工具，而是自己亂答 | `description` 寫得不清楚，模型不知道該用 | 在 `description` 寫明「什麼時候要用這個工具」 |
| 平行呼叫的結果只送回一個 | 迴圈裡只處理了第一張紙條 | 用 for 迴圈處理 `tool_calls` 裡的**每一個** |

## 【本章小結】

1. 原生工具呼叫把手刻版的「自訂紙條」換成 API 的正式格式：工具說明放在 `tools`（JSON Schema），模型的請求是 `function_call`，工具結果用 `function_response` 送回。
2. JSON Schema 可以精確描述參數：型別、`enum`（只能選這些值）、`required`（必填），比 prompt 更能防止模型填錯參數。
3. **核心機制完全沒變**：模型只會說，程式負責執行，結果要送回模型；工具定義每次呼叫都要送。
4. 新一代 Gemini 模型的工具請求附有思考簽章，要把原始內容（`raw`）原封不動送回；本書用通用格式的 `tool_calls` 和 `tool` 角色記錄對話，由 `call_llm_tools()` 轉換。
5. 原生版支援平行呼叫（一次要求多個互不相關的工具），但「有先後順序」的多步驟問題，仍然需要下一章的迴圈。
