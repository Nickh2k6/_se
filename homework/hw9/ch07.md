# 第 7 章　Agent 誕生

## 【本章重點】

**Agent ＝ LLM ＋ 工具 ＋ 迴圈。** 前兩章的工具呼叫只能進行「一輪」；只要把它放進 `while` 迴圈，讓程式**一直把工具結果送回給模型，直到模型說「我可以回答了」為止**，就得到一個 Agent。
這個迴圈的每一圈都是：**思考 → 行動 → 觀察 → 再思考**，這種「邊推理、邊行動」的做法叫做 **ReAct**。
關鍵差別在於：**要用幾個工具、用哪些、照什麼順序，不再由你寫死，而是由模型自己決定。**

---

## 【為什麼需要這一章】

第 5、6 章都卡在同一個問題：

```text
你：明天有什麼課？
  [程式執行] get_current_time({}) → 2026-11-27 星期五 21:30
小助理：（模型還想再使用 get_schedule，但這個函式只支援一輪工具呼叫）
```

模型其實很清楚下一步要做什麼（查星期六的課表），是**我們的程式**沒給它機會。`ask_with_tool()` 和 `ask_with_native_tools()` 都寫死了「最多一輪」。

你可能會想：那改成「最多兩輪」就好了？但問題可能需要三步、五步，或者一步都不需要。**你不可能事先知道每個問題要幾步。**

這一章要解決的問題是：**怎麼讓模型「想用幾次工具就用幾次」，直到它自己覺得可以回答為止？**

---

## 【觀念解說】

### 7.1 問題：一個需要好幾步的問題

看看這個問題：

> 「今天最後一堂課幾點下課？金門今天會下雨嗎？要不要帶傘？」

要回答它，需要依序做這些事：

```text
  ① 今天星期幾？            → 用 get_current_time        → 「星期五」
  ② 星期五有什麼課？         → 用 get_schedule(星期五)     → 「09:10-12:00 程式設計實習」
  ③ 金門今天天氣？           → 用 get_weather(金門)        → 「多雲，降雨機率 20%」
  ④ 綜合起來回答             → 「12:00 下課，降雨機率低，不太需要帶傘」
```

注意第 ② 步**必須等第 ① 步的結果**，才知道要查哪一天。這種「下一步取決於上一步結果」的問題，就算有平行呼叫也沒辦法一次完成。

### 7.2 Agent 是什麼

**Agent（代理人、智慧代理）**：一個能**自己決定下一步要做什麼**、使用工具來完成目標的程式。給它一個目標，它會自己規劃步驟、執行、檢查結果，直到完成。

**比喻：會自己查資料的實習生。**

| | 普通的助理（第 5、6 章） | 實習生 Agent（本章） |
|---|---|---|
| 你交代的事 | 「去查星期五的課表。」 | 「幫我看今天幾點下課、要不要帶傘。」 |
| 它怎麼做 | 查完一樣東西就回來報告 | 自己想：要先知道今天星期幾 → 再查課表 → 再查天氣 → 整理好再報告 |
| 誰決定步驟 | 你 | 它自己 |

**回到技術說明：**

```text
  ┌─────────────────────── Agent ───────────────────────┐
  │                                                     │
  │      LLM（大腦）    ＋    工具（手）    ＋    迴圈（不停地做）      │
  │      決定下一步           實際執行          直到完成為止          │
  │                                                     │
  └─────────────────────────────────────────────────────┘
```

- **LLM**：第 2 章學會怎麼呼叫，負責「思考、決定」。
- **工具**：第 5、6 章學會怎麼讓模型使用，負責「動手」。
- **迴圈**：本章要加上的，讓前兩者可以**反覆合作**。

**Workflow 和 Agent 的差別**

有時候你會聽到 **workflow（工作流程）** 這個詞，它和 Agent 很容易搞混：

| | Workflow（工作流程） | Agent（代理人） |
|---|---|---|
| 步驟由誰決定 | 程式設計師事先寫死 | 模型執行時自己決定 |
| 範例 | 「一定先查時間，再查課表，再回答」 | 「看問題需要什麼，就查什麼」 |
| 優點 | 可預測、好除錯、省錢 | 有彈性，能處理沒想過的問題 |
| 缺點 | 遇到沒想過的問題就不行 | 比較難預測，可能繞遠路、花比較多錢 |

第 5、6 章的 `ask_with_tool()` 比較像 workflow（固定「最多一輪」），本章的 `run_agent()` 才是 Agent。實務上兩者常常混合使用：能寫死的就寫死，真正需要彈性的地方才交給 Agent。

### 7.3 思考 → 行動 → 觀察 → 再思考

Agent 迴圈的每一圈，都在做同樣的四件事：

```text
                    ┌──────────────────────────┐
                    │   使用者的問題 / 目標       │
                    └────────────┬─────────────┘
                                 ▼
                    ┌──────────────────────────┐
          ┌───────▶ │ ① 思考（Thought）          │  LLM：還缺什麼資訊？下一步做什麼？
          │         └────────────┬─────────────┘
          │                      ▼
          │         ┌──────────────────────────┐     不需要工具了
          │         │   要用工具嗎？              │ ────────────────▶ 最終回答，結束
          │         └────────────┬─────────────┘
          │                      │ 要
          │                      ▼
          │         ┌──────────────────────────┐
          │         │ ② 行動（Action）           │  LLM 寫紙條 → 你的程式執行工具
          │         └────────────┬─────────────┘
          │                      ▼
          │         ┌──────────────────────────┐
          │         │ ③ 觀察（Observation）      │  工具結果加進 messages
          │         └────────────┬─────────────┘
          │                      │
          └──── ④ 再思考 ◀────────┘              帶著新的資訊，回到 ①
```

和第 3 章的聊天迴圈比較：

| | 第 3 章：聊天迴圈 | 本章：Agent 迴圈 |
|---|---|---|
| 每一圈等誰 | 等**人**輸入下一句話 | 等**工具**的執行結果 |
| 新加進 messages 的 | 使用者說的話 | 工具結果（`tool` 角色） |
| 什麼時候結束 | 使用者輸入 exit | **模型**決定不再用工具，給出最終回答 |

兩個迴圈的骨架其實一模一樣：**「把新資訊加進 messages → 呼叫 LLM → 處理回應」**，差別只在「新資訊從哪裡來」。

### 7.4 ReAct：邊推理、邊行動

**ReAct（Reasoning + Acting，推理＋行動）**：2022 年 Google 與普林斯頓大學的研究者提出的方法。核心想法是：讓模型**交替地「寫出推理」和「採取行動」**，而不是一次想完所有步驟，或是只行動不思考。

ReAct 論文裡，模型的輸出長這樣：

```text
Thought 1: 我需要知道今天星期幾，才能查課表。
Action 1: get_current_time[]
Observation 1: 2026-11-27 星期五 21:30
Thought 2: 今天是星期五，接著查星期五的課表。
Action 2: get_schedule[星期五]
Observation 2: 09:10-12:00 程式設計實習
Thought 3: 還需要天氣資訊。
...
```

為什麼要「把想法寫出來」？

1. **模型會想得比較好**：第 1 章說過，模型是「接龍」產生文字的。先寫出「我需要知道今天星期幾」，接下來接出「用 get_current_time」的機率就大大提高。這就像寫數學題時把計算過程寫出來，比較不容易算錯。
2. **你看得懂它在想什麼**：Agent 出錯時，看它的推理過程，很快就知道是哪一步想錯了。

> **「思考」和第 2 章的 thinking 有什麼不同？**
> 第 2 章的思考 token 是模型在**內部**進行的推理，一般不會出現在回答裡。
> 本章的「思考」是我們在 prompt 裡**要求模型寫出來**的一句話，會出現在回應的文字中，所以程式印得出來。
> 兩者目的相同，都是讓模型先想再做；差別是後者「看得見」。

現在的 API 有原生工具呼叫（第 6 章），所以「行動」不用再照論文的文字格式寫，直接用 `function_call` 就好。但「先寫出想法」這個精神，我們用 prompt 保留下來：

```python
AGENT_PROMPT = """……每次使用工具之前，先用一句話寫出你的想法……"""
```

模型回應時，就可能**同時**有一段文字（思考）和一個 `function_call`（行動）。

### 7.5 用 while 迴圈寫出 `run_agent()`

把第 6 章 `ask_with_native_tools()` 的「一輪」改成「迴圈」：

```text
  ask_with_native_tools()（第 6 章）          run_agent()（本章）
  ────────────────────────────────           ────────────────────────────────
  呼叫 LLM                                   while 還沒超過最大步數：
  如果沒有工具請求 → 回答                         呼叫 LLM
  執行工具、送回結果                              如果沒有工具請求 → 回答，結束
  呼叫 LLM                                       執行工具、送回結果
  如果還有工具請求 → 放棄 ✗                       （回到迴圈開頭，再呼叫 LLM）
  回答
```

改動其實很小：**把「執行工具 → 再呼叫 LLM」這段放進迴圈裡，重複到模型不再要求工具為止。**

**什麼時候結束？**

1. **正常結束**：模型的回應裡沒有工具請求 → 它認為資訊夠了，這段文字就是最終回答。
2. **保險**：迴圈最多跑 `max_steps` 圈。萬一模型一直要求工具、停不下來，也不會無限執行下去。

第 2 點是一個簡單的保險，第 8 章會更完整地討論「Agent 什麼時候該停」。

### 7.6 把每一步印出來

Agent 是自己決定步驟的，如果只印最終回答，你完全不知道它中間做了什麼。所以每一步都印出：

```text
[第 1 步] 思考：我需要先知道今天是星期幾。
          行動：get_current_time()
          觀察：2026-11-27 星期五 21:30
[第 2 步] 思考：今天是星期五，查星期五的課表。
          行動：get_schedule(day="星期五")
          觀察：{"day": "星期五", "courses": [...]}
[第 3 步] 最終回答：……
```

這就是第 0 章「先看終點」裡展示的樣子。現在你知道它是怎麼做出來的了：

- **思考**：回應的文字部分（`response["text"]`）
- **行動**：回應的工具請求（`response["tool_calls"]`）
- **觀察**：`run_tool()` 的回傳值

```python
def calculator(expression):
    """計算數學算式，例如 "(3 + 4) * 2"。只允許數字和 + - * / ( ) ."""

    if not set(expression) <= allowed:

    return eval(expression, {"__builtins__": {}}, {})

def call_llm_tools(messages, temperature=None, max_output_tokens=1024):
    """
    原生工具呼叫版的 call_llm：把通用格式的 messages 連同工具宣告一起送給 Gemini。
    回傳 dict：{"text": 文字回答, "tool_calls": [{"name": ..., "args": {...}}], "raw": 模型的原始回應內容}
    """
    system_text = None
    contents = []

    for msg in messages:
        if msg["role"] == "system":
            system_text = msg["content"]

        elif msg["role"] == "user":
            contents.append(types.Content(role="user", parts=[types.Part.from_text(text=msg["content"])]))

        elif msg["role"] == "assistant":
            if msg.get("raw") is not None:
                contents.append(msg["raw"])
            else:
                parts = []
                if msg.get("content"):
                    parts.append(types.Part.from_text(text=msg["content"]))
                for call in msg.get("tool_calls", []):
                    parts.append(types.Part(function_call=types.FunctionCall(name=call["name"], args=call["args"])))
                contents.append(types.Content(role="model", parts=parts))

        elif msg["role"] == "tool":
            part = types.Part.from_function_response(name=msg["name"], response={"result": msg["content"]})
            last = contents[-1] if contents else None
            if last is not None and last.role == "user" and last.parts[0].function_response is not None:
                last.parts.append(part)
            else:
                contents.append(types.Content(role="user", parts=[part]))

    response = client.models.generate_content(
        model=MODEL_NAME,
        contents=contents,
        config=types.GenerateContentConfig(
            system_instruction=system_text,
            temperature=temperature,
            max_output_tokens=max_output_tokens,
            tools=[types.Tool(function_declarations=TOOL_DECLARATIONS)],
        ),
    )

    content = response.candidates[0].content
    text = ""
    tool_calls = []
    if content is not None and content.parts:
        for part in content.parts:
            if part.function_call is not None:
                tool_calls.append({"name": part.function_call.name, "args": dict(part.function_call.args or {})})
            elif part.text and not part.thought:
                text += part.text

    return {"text": text, "tool_calls": tool_calls, "raw": content}


def mock_next_action(question, used):
    """假的 LLM 的「大腦」：根據問題裡的關鍵字，決定下一步要用哪個工具"""
    day = None
    for d in WEEKDAYS:
        if d in question:
            day = d
            break

    need_time = any(k in question for k in ["幾點", "幾號", "星期幾", "時間", "日期"])
    if "課" in question and day is None:
        need_time = True
    if need_time and "get_current_time" not in used:
        return {"tool": "get_current_time", "args": {}}

    if "課" in question and "get_schedule" not in used:
        if day is None:
            time_text = used.get("get_current_time", "")
            for i, d in enumerate(WEEKDAYS):
                if d in time_text:
                    day = WEEKDAYS[(i + 1) % 7] if "明天" in question else d
                    break
        if day is not None:
            return {"tool": "get_schedule", "args": {"day": day}}

    if any(k in question for k in ["天氣", "雨", "騎車", "傘"]) and "get_weather" not in used:
        city = "台北" if "台北" in question else "金門"
        return {"tool": "get_weather", "args": {"city": city}}

    question_math = question.replace("乘以", "*").replace("除以", "/").replace("加", "+").replace("減", "-")
    match = re.search(r"\d[\d\.\s\(\)]*[\+\-\*/][\d\.\s\+\-\*/\(\)]*\d", question_math)
    if match and "calculator" not in used:
        return {"tool": "calculator", "args": {"expression": match.group()}}

    if used:
        summary = "；".join(f"{name} → {result}" for name, result in used.items())
        return {"answer": f"（mock）根據查詢結果：{summary}"}
    return {"answer": "（mock）你好！我是假的校園小助理，只會用規則回答問題。"}


# 有 API key：llm_tools 指向真的；沒有的話，程式 7-3 會設定成 mock
if not USE_MOCK:
    llm_tools = call_llm_tools

print("環境準備完成！USE_MOCK =", USE_MOCK)
```

**逐段解說：**

這段是第 6 章程式 6-0（工具、`run_tool()`、`mock_next_action()`）、6-1（`TOOL_DECLARATIONS`）和 6-3（`call_llm_tools()`）的合併，內容完全相同，每一行在第 5、6 章都解說過。

### 程式 7-1：Agent 的提示詞與主迴圈 `run_agent()`

這段只是定義函式，**不需要 API key**。

```python
# Agent 的工作方式（和 SYSTEM_PROMPT 組合使用）
AGENT_PROMPT = """你可以使用工具來完成任務。請照以下方式工作：
1. 先想清楚：要回答這個問題，還缺少哪些資訊？
2. 每次使用工具之前，先用一句話寫出你的想法，例如「我需要先知道今天是星期幾」。
3. 拿到工具結果後，判斷資訊是否足夠：不夠就繼續使用工具，夠了就直接回答使用者。
4. 工具查得到的資訊，不要自己猜。"""


def format_call(name, args):
    """把工具請求排成 get_schedule(day="星期五") 這種好讀的樣子"""
    args_text = ", ".join(f"{key}={json.dumps(value, ensure_ascii=False)}" for key, value in args.items())
    return f"{name}({args_text})"


def run_agent(user_input, max_steps=10):
    """
    Agent 主迴圈：思考 → 行動 → 觀察 → 再思考，直到模型給出最終回答。
    max_steps：最多跑幾圈，避免停不下來。
    """
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT + "\n\n" + AGENT_PROMPT},
        {"role": "user", "content": user_input},
    ]

    step = 0
    while step < max_steps:
        step += 1

        # ① 思考：把目前為止的所有資訊交給模型，讓它決定下一步
        response = llm_tools(messages, temperature=0)

        # 沒有工具請求 → 模型認為資訊夠了，這就是最終回答
        if not response["tool_calls"]:
            print(f"[第 {step} 步] 最終回答：{response['text'].strip()}")
            return response["text"]

        # 有工具請求：先印出模型寫的想法（如果有的話）
        if response["text"].strip():
            print(f"[第 {step} 步] 思考：{response['text'].strip()}")
        else:
            print(f"[第 {step} 步]")

        # 把模型的紙條記進對話
        messages.append({
            "role": "assistant",
            "content": response["text"],
            "tool_calls": response["tool_calls"],
            "raw": response["raw"],
        })

        # ② 行動：由程式執行每一個工具
        for call in response["tool_calls"]:
            print(f"          行動：{format_call(call['name'], call['args'])}")
            result = run_tool(call["name"], call["args"])

            # ③ 觀察：把結果記進對話，下一圈模型就看得到
            print(f"          觀察：{result}")
            messages.append({"role": "tool", "name": call["name"], "content": result})

        # ④ 回到迴圈開頭，帶著新的資訊再思考

    # 跑完 max_steps 圈還沒結束
    print(f"[停止] 已經跑了 {max_steps} 步，還沒有得到最終回答。")
    return "（抱歉，這個問題太複雜了，我沒辦法在限定的步數內完成。）"


print("run_agent() 準備完成！")
```

**逐段解說：**

- **`AGENT_PROMPT`**：照 7.3、7.4 節的流程寫成工作守則。第 2 點「先用一句話寫出你的想法」就是 ReAct 的精神；第 3 點告訴模型「資訊夠了就回答」，這是迴圈能正常結束的關鍵。
- **`format_call(name, args)`**：純粹為了印出來好看。`json.dumps(value, ensure_ascii=False)` 會把字串加上雙引號，例如 `day="星期五"`。`", ".join(...)` 把多個參數用逗號接起來。
- **`run_agent()` 的結構**，對照 7.3 節的圖：
  - **建立 messages**：system 是 `SYSTEM_PROMPT` 加上 `AGENT_PROMPT`。
  - **`while step < max_steps`**：迴圈本體。`step` 從 0 開始，每圈加 1。
  - **① 思考**：`llm_tools(messages, temperature=0)`。注意每一圈送出的 `messages` 都比上一圈更長，因為裡面多了新的工具結果（第 3 章學過的對話記憶）。
  - **結束條件**：`if not response["tool_calls"]`，模型沒有要用工具，就把文字當最終回答，`return` 跳出整個函式。
  - **印出思考**：模型有寫文字就印出來；有些時候模型會直接寫紙條、不寫想法，那就只印步數。
  - **記錄紙條**：和第 6 章一樣，assistant 訊息要帶 `tool_calls` 和 `raw`。
  - **② 行動 ＋ ③ 觀察**：for 迴圈處理每一張紙條（可能有平行呼叫），執行、印出、記錄。
  - **④ 再思考**：for 迴圈結束後，自然回到 `while` 的開頭，再呼叫一次 LLM。
  - **超過 `max_steps`**：`while` 條件不成立而離開迴圈，回傳一句道歉。

**和第 6 章 `ask_with_native_tools()` 比較**，真正新增的只有兩件事：`while` 迴圈，以及印出每一步。Agent 並不神秘，**它就是把工具呼叫放進迴圈裡。**

**預期輸出：**

```text
run_agent() 準備完成！
```

### 程式 7-3：用 mock 跑 Agent —— 不花錢也能看懂流程

這段**不需要 API key**。我們升級 `mock_llm_tools()`，讓它在要求工具時，也會寫一句「思考」，然後用它來跑 `run_agent()`。

```python
# mock 在使用各個工具前，會寫出的想法
MOCK_THOUGHTS = {
    "get_current_time": "我需要先知道現在的日期和星期幾。",
    "get_schedule": "接著查課表。",
    "get_weather": "還需要查天氣。",
    "calculator": "這需要計算，我用計算機算。",
}


def mock_llm_tools(messages, temperature=None, max_output_tokens=1024):
    """
    假的原生工具呼叫：參數和回傳格式都和 call_llm_tools() 一樣。
    要求工具時，會同時寫一句想法（模擬 ReAct 的「思考」）。
    """
    # 找出使用者原本的問題：最後一則 user 訊息
    question = ""
    question_index = 0
    for i in range(len(messages) - 1, -1, -1):
        if messages[i]["role"] == "user":
            question = messages[i]["content"]
            question_index = i
            break

    # 收集這個問題之後，已經拿到的工具結果
    used = {}
    for msg in messages[question_index + 1:]:
        if msg["role"] == "tool":
            used[msg["name"]] = msg["content"]

    # 交給「大腦」決定下一步
    action = mock_next_action(question, used)

    if "tool" in action:
        thought = MOCK_THOUGHTS.get(action["tool"], "")
        return {"text": thought, "tool_calls": [{"name": action["tool"], "args": action["args"]}], "raw": None}
    return {"text": action["answer"], "tool_calls": [], "raw": None}


# ===== 開關 =====

# 不管開關怎麼設，這裡都暫時用 mock 跑一次，讓大家看到同樣的流程
```

**逐段解說：**

- **`MOCK_THOUGHTS`**：每個工具對應一句固定的想法。真正的模型會根據情況寫出不同的想法，mock 只能用固定句子模擬。
- **`mock_llm_tools()`**：和第 6 章的版本幾乎一樣，只改了一行：要求工具時，`text` 不再是空字串，而是 `MOCK_THOUGHTS` 裡對應的那句話。`.get(名稱, "")` 在找不到時回傳空字串。

- **暫時切換**：`real_llm_tools = llm_tools` 先把原本的設定存起來，跑完再換回去。這樣有 API key 的讀者跑完這段，`llm_tools` 還是指向真的模型。

## 【常見錯誤】

| 錯誤情況 | 原因 | 解決方式 |
|---------|------|---------|
| Agent 一直重複呼叫同一個工具 | 工具結果沒有加進 messages，模型每一圈看到的都一樣 | 確認每個工具結果都 `append` 成 `tool` 訊息 |
| 第二圈開始出錯，訊息提到 function call / response 不對應 | 只加了工具結果，沒加模型的紙條；或紙條和結果的數量不一致 | 先 `append` assistant（含 `tool_calls`、`raw`），再為**每一張**紙條 `append` 一個 tool 結果 |
| 程式跑很久都沒結束 | 用了 `while True` 卻沒有步數上限 | 一定要有 `max_steps` 之類的保險 |
| Agent 沒有印出「思考」 | 模型這一步選擇直接寫紙條，沒有寫文字 | 這是正常的；`AGENT_PROMPT` 只能鼓勵，不能強迫 |
| 最終回答是空字串 | 模型回應被切斷或被擋下 | 檢查第 2 章的停止原因；第 8 章會處理 |
| 把 `messages` 寫在 `run_agent()` 外面，問題之間互相干擾 | 全域變數沒有重設，上一題的工具結果混進下一題 | 在 `run_agent()` 裡面建立 `messages` |
| 程式 7-3 跑完後，真的模型變成假的 | 暫時切換成 mock 後忘了換回來 | 用 `real_llm_tools` 存起來，跑完再設定回去 |
| 工具丟出例外，整個 Agent 停止 | 例如模型拼錯工具名稱、除以零 | 第 8 章的主題 |

---

## 【本章小結】

1. **Agent ＝ LLM ＋ 工具 ＋ 迴圈**：把「工具呼叫」放進 `while` 迴圈，讓程式一直把工具結果送回模型，直到模型不再要求工具。
2. 每一圈都是 **思考 → 行動 → 觀察 → 再思考**；結束條件是「模型的回應裡沒有工具請求」，再加上 `max_steps` 當保險。
3. **ReAct** 的核心是讓模型交替地寫出推理、採取行動；寫出想法能讓模型想得更好，也讓人看得懂它在做什麼。
4. Agent 和 workflow 的差別在於「步驟由誰決定」：workflow 由程式設計師寫死，Agent 由模型在執行時自己決定。
5. `run_agent()` 不需要知道背後是真的模型還是 mock；只要回傳格式一樣，迴圈就能運作。
