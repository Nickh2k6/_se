# 第 3 章　讓它記得你

## 【本章重點】

**LLM API 本身不會記得任何事。** 每次呼叫都是全新的開始，它不知道你上一句說了什麼。
想讓它「記得」，方法只有一個：**你的程式自己用一個 list（`chat_history`）把整段對話存起來，每次呼叫時全部重送一次。**
這個做法很簡單，但代價是：對話越長，每次送出的 token 越多，費用和等待時間都會一直增加，最後還會撞到模型能讀的長度上限。

---

## 【為什麼需要這一章】

第 2 章我們做出了 `call_llm(messages)`，可以問一個問題、拿到一個回答。但試著連問兩句：

```text
你：我叫小明。
模型：你好小明！很高興認識你。

你：我叫什麼名字？
模型：抱歉，我不知道你的名字。
```

模型馬上就忘了。第 2 章的做法是「**一問一答**」，每次呼叫之間完全沒有關聯。這樣做不出聊天機器人，更不可能做出要連續處理好幾步的 Agent。

這一章要解決的問題是：**怎麼讓模型「記得」前面的對話？**

---

## 【觀念解說】

### 3.1 先做實驗：模型真的會忘記

請先跑下面【動手做】的程式 3-1。你會親眼看到：第一次呼叫告訴它名字，第二次呼叫它就不記得了。

這不是模型「記性差」，而是它**根本沒有機會記**。原因在下一節。

### 3.2 無狀態（stateless）：每次都是第一次見面

**無狀態（stateless）**：一個系統不會保留「之前發生過什麼」的資訊，每次請求都被當成完全獨立的事件處理。

**比喻：每次都換人的客服專線。**

你打電話給客服說「我叫小明，訂單有問題」。掛掉之後再打一次，接電話的是**另一個客服人員**，他完全不知道你剛剛打過。你只好把整件事**從頭再講一次**。

LLM API 就是這樣：

```text
  第 1 次呼叫                              第 2 次呼叫
  ───────────                             ───────────
  送出：「我叫小明。」                     送出：「我叫什麼名字？」
     │                                       │
     ▼                                       ▼
  ┌──────┐                                ┌──────┐
  │ LLM  │ → 「你好小明！」                 │ LLM  │ → 「我不知道你的名字。」
  └──────┘                                └──────┘
     ↑                                       ↑
  呼叫結束後，什麼都沒留下                  它只看得到這一次送來的內容
```

**回到技術說明：為什麼 API 要設計成無狀態？**

- **伺服器簡單、好擴充**：Google 有成千上萬台伺服器同時服務全世界。如果每台都要記住每個使用者的對話，第 1 次和第 2 次請求就必須送到同一台，非常麻煩。無狀態的話，任何一台都能處理任何請求。
- **你有完全的控制權**：要送什麼、刪什麼、改什麼，都由你的程式決定。這在後面的章節非常重要（例如第 8 章刪掉過長的資料、第 9 章檢查危險內容）。

還記得第 1 章說的嗎？**模型是一份訓練完就固定的檔案。** 你跟它聊天，不會改變它裡面的任何一個參數。它唯一能「看到」的，就是**這一次請求裡送過去的文字**。

### 3.3 解法：用 list 把對話存起來，每次全部重送

既然模型只看得到「這一次送過去的東西」，那就**每次都把前面的對話一起送過去**。

回到客服的比喻：既然每次都換人，那你就準備一份**對話紀錄**，每次打電話都先把紀錄念一遍，再說新的問題。新的客服聽完紀錄，就「好像記得」你了。

我們用一個 list 來保存對話，叫做 `chat_history`（全書固定用這個名稱）：

```python
chat_history = [
    {"role": "system",    "content": "你是金門大學的校園小助理。"},
    {"role": "user",      "content": "我叫小明。"},
    {"role": "assistant", "content": "你好小明！很高興認識你。"},
    {"role": "user",      "content": "我叫什麼名字？"},
]
```

這就是第 2 章說的**通用格式 messages**。第 2 章只用到 `system` 和 `user`，現在終於用到 `assistant` 了：它用來記錄**模型之前說過的話**。

**每一輪對話，`chat_history` 的變化：**

```text
  一開始       [system]

  使用者說話   [system, user①]                          ← append 使用者的話
  呼叫 LLM     送出整個 list ─────▶ LLM ─────▶ 回答①
  存下回答     [system, user①, assistant①]              ← append 模型的回答

  使用者說話   [system, user①, assistant①, user②]
  呼叫 LLM     送出整個 list ─────▶ LLM ─────▶ 回答②    ← 這次 LLM 看得到 user①，所以「記得」
  存下回答     [system, user①, assistant①, user②, assistant②]

  ……每一輪 list 都變長兩則
```

重點整理成三個步驟，每一輪都一樣：

1. 把**使用者的話** `append` 進 `chat_history`
2. 把**整個** `chat_history` 交給 `call_llm()`
3. 把**模型的回答** `append` 進 `chat_history`

> **常見誤解**：「模型記得我」其實是錯覺。真正記住對話的是**你的程式**裡那個 list，模型每次都是從頭讀完整份紀錄，再接著回答。
>
> 有些新的 API（例如第 11 章會提到的 Gemini Interactions API）提供「伺服器幫你保存對話」的功能。但本質完全一樣：只是把這個 list 從你的程式搬到 Google 的伺服器上保管，每次還是要把整段歷史交給模型讀。

### 3.4 聊天迴圈

有了 `chat_history`，再加上 `while True` 迴圈和 `input()`，就能做出一個可以一直聊下去的聊天機器人：

```text
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
   ┌─────────┐   輸入 exit   ┌──────┐          │
   │ input() │ ────────────▶ │ 結束 │          │
   └─────────┘               └──────┘          │
        │ 其他文字                              │
        ▼                                      │
   append 使用者的話                            │
        │                                      │
        ▼                                      │
   call_llm(chat_history)                      │
        │                                      │
        ▼                                      │
   append 模型的回答、印出來 ────────────────────┘
```

這個迴圈就是程式 3-3。之後第 7 章的 Agent 迴圈，也是從這個樣子長出來的。

### 3.5 上下文長度（context window）

`chat_history` 每一輪都會變長，那可以無限長下去嗎？不行。

**上下文長度（context window，也譯作「上下文視窗」）**：模型**一次能讀進去的 token 數量上限**，包含你送進去的所有訊息，以及它要產生的回答。

**比喻：考試能帶的 A4 小抄。**

小抄的大小是固定的。重點越寫越多，寫滿了就只能擦掉舊的、才能寫新的。模型的上下文長度就是這張小抄的大小。

目前的 Gemini 模型上下文長度大多很大（常見是一百萬 token 左右的等級，實際數字請查官方 Models 頁面），一般聊天很難塞滿。但「塞得下」不代表「沒問題」：

| 問題 | 說明 |
|------|------|
| **費用** | 每一輪都要把全部歷史重送一次，輸入 token 越來越多（下一節詳細算） |
| **速度** | 模型要讀的東西越多，回應越慢 |
| **注意力分散** | 內容太長時，模型比較容易忽略中間的細節，回答品質可能下降 |
| **撞到上限** | 真的超過上限時，API 會直接回傳錯誤 |

> 第 1 章說「模型可以看前面全部的文字」，這裡的「全部」，指的就是「上下文長度以內」的全部。

### 3.6 成本問題：為什麼越聊越貴

這是初學者最容易忽略的地方。假設每一則訊息（不管是使用者說的還是模型回答的）都大約 50 個 token：

```text
  第 1 輪送出：[system, user①]                                  ≈ 100 token
  第 2 輪送出：[system, user①, asst①, user②]                    ≈ 200 token
  第 3 輪送出：[system, user①, asst①, user②, asst②, user③]      ≈ 300 token
  ……
  第 10 輪送出：                                                ≈ 1000 token
```

每一輪的輸入**越來越大**，而且**每一輪都要付錢**。所以 10 輪下來的累積輸入不是 1000 token，而是 100 + 200 + ⋯⋯ + 1000 = **5500 token**。

對話輪數變成 2 倍，累積費用大約變成 **4 倍**。程式 3-4 會用 Python 算給你看。

**常見的解決方法：只送最近的對話（截斷，truncation）**

```text
  完整的 chat_history（保存在程式裡）：
  [system, u①, a①, u②, a②, u③, a③, u④, a④, u⑤]

  實際送給 LLM 的（只保留 system ＋ 最近幾則）：
  [system,                     u③, a③, u④, a④, u⑤]
            ↑ 太舊的先不送
```

- **system 一定要留**：那是角色和規則，丟掉的話模型就「忘了自己是誰」。
- **保留最近幾則**：大部分時候，最近的對話最重要。
- **代價**：太舊的內容模型就真的看不到了。如果使用者在第 1 輪說了名字，第 20 輪可能就忘了。

第 10 章會介紹更聰明的做法：把重要的事情（例如使用者的名字）另外存成「長期記憶」。

### 程式 3-0：準備環境（接續第 2 章）

如果你是接著第 2 章在同一個筆記本裡執行，而且執行階段沒有重新啟動過，可以跳過這一段。否則請先執行它，把第 2 章的東西準備好。

```python

from google import genai
from google.genai import types
from google.colab import userdata

# 從 Colab 密鑰讀取 API key
api_key = userdata.get("GEMINI_API_KEY")

# 全書使用的模型名稱
MODEL_NAME = "gemini-3.5-flash-lite"

# 建立連線物件
client = genai.Client(api_key=api_key)


def call_llm(messages, temperature=None, max_output_tokens=1024):
    """
    把通用格式的 messages 送給 Gemini，回傳模型的文字回答。
    messages 的格式：[{"role": "system" / "user" / "assistant", "content": "文字"}, ...]
    """
    system_text = None
    contents = []

    # 把通用格式轉成 Gemini 的格式
    for msg in messages:
        if msg["role"] == "system":
            # system 不放進 contents，而是另外交給 system_instruction
            system_text = msg["content"]
        else:
            # Gemini 把 assistant 叫做 model
            role = "model" if msg["role"] == "assistant" else "user"
            contents.append({"role": role, "parts": [{"text": msg["content"]}]})

    response = client.models.generate_content(
        model=MODEL_NAME,
        contents=contents,
        config=types.GenerateContentConfig(
            system_instruction=system_text,
            temperature=temperature,
            max_output_tokens=max_output_tokens,
        ),
    )

    # 回答是空的時候 response.text 會是 None，統一轉成空字串比較好處理
    return response.text or ""


print("環境準備完成！")
```

### 程式 3-2：用 `chat_history` 讓它記得

```python
# 建立對話紀錄，先放入 system 訊息
chat_history = [
    {"role": "system", "content": "你是金門大學的校園小助理，回答一律使用繁體中文，而且簡短。"}
]

# ===== 第 1 輪 =====
# 步驟 1：把使用者的話加進紀錄
chat_history.append({"role": "user", "content": "我叫小明，是資工系一年級的學生。"})
# 步驟 2：把「整份紀錄」交給 LLM
reply = call_llm(chat_history)
# 步驟 3：把模型的回答也加進紀錄
chat_history.append({"role": "assistant", "content": reply})
print("第 1 輪回答：", reply)

# ===== 第 2 輪 =====
chat_history.append({"role": "user", "content": "我叫什麼名字？讀哪一系？"})
reply = call_llm(chat_history)
chat_history.append({"role": "assistant", "content": reply})
print("第 2 輪回答：", reply)

# 看看現在紀錄裡有什麼
print("\n===== 目前的 chat_history =====")
for msg in chat_history:
    print(f"[{msg['role']}] {msg['content']}")
```

**逐段解說：**

- **建立 `chat_history`**：一開始只有一則 `system` 訊息，設定小助理的身分。
- **每一輪都是同樣的三個步驟**：`append` 使用者的話 → `call_llm(chat_history)` 送出**整份**紀錄 → `append` 模型的回答。
- **第 2 輪呼叫時**，送出去的 `chat_history` 裡有 4 則訊息：system、第 1 輪的使用者、第 1 輪的模型回答、第 2 輪的使用者。所以模型「看得到」小明的名字。
- **最後的 for 迴圈**：把整份紀錄印出來，讓你看到 list 裡實際存了什麼。

**預期輸出：**

```text
第 1 輪回答： 你好小明！歡迎加入資工系，有任何校園問題都可以問我。
第 2 輪回答： 你叫小明，讀資工系一年級。

===== 目前的 chat_history =====
[system] 你是金門大學的校園小助理，回答一律使用繁體中文，而且簡短。
[user] 我叫小明，是資工系一年級的學生。
[assistant] 你好小明！歡迎加入資工系，有任何校園問題都可以問我。
[user] 我叫什麼名字？讀哪一系？
[assistant] 你叫小明，讀資工系一年級。
```

和程式 3-1 比較：**模型沒有變，變的是我們送過去的內容。**

### 程式 3-3：做出聊天迴圈

把程式 3-2 重複的三個步驟放進 `while` 迴圈，就是一個真正的聊天機器人：

```python
def chat():
    """校園小助理聊天機器人：輸入 exit 結束"""
    # 每次開始聊天，都建立一份新的對話紀錄
    chat_history = [
        {"role": "system", "content": "你是金門大學的校園小助理，回答一律使用繁體中文，而且簡短。"}
    ]
    print("校園小助理：你好！有什麼可以幫你的嗎？（輸入 exit 結束）")

    while True:
        user_input = input("你：").strip()

        # 輸入 exit 就結束迴圈
        if user_input.lower() == "exit":
            print("校園小助理：掰掰，祝你有美好的一天！")
            break

        # 什麼都沒輸入就直接進入下一輪，不浪費一次 API 呼叫
        if user_input == "":
            continue

        # 三個步驟：記下使用者的話 → 送出整份紀錄 → 記下模型的回答
        chat_history.append({"role": "user", "content": user_input})
        reply = call_llm(chat_history)
        chat_history.append({"role": "assistant", "content": reply})

        print("校園小助理：", reply)

    # 聊天結束後，回傳整份紀錄，方便之後檢查
    return chat_history


history = chat()
```

**逐段解說：**

- **`chat()` 函式**：把整個聊天機器人包成一個函式，`chat_history` 是函式裡的區域變數，每次呼叫 `chat()` 都從新的對話開始。
- **`input("你：").strip()`**：Colab 會在輸出區出現一個輸入框，等你打字並按 Enter。`.strip()` 去掉前後的空白。
- **`user_input.lower() == "exit"`**：`.lower()` 把英文轉成小寫，這樣輸入 `EXIT` 或 `Exit` 也能結束。
- **`if user_input == "": continue`**：直接按 Enter 沒打字時，跳過這一輪，不要白白呼叫 API。
- **中間三行**：和程式 3-2 一模一樣的三個步驟。
- **`return chat_history`**：聊完之後把紀錄回傳，存在外面的 `history` 變數裡，你可以之後印出來看。

**預期輸出（你輸入的內容不同，回答就會不同）：**

```text
校園小助理：你好！有什麼可以幫你的嗎？（輸入 exit 結束）
你：我是小明，這學期修了 5 門課
校園小助理： 你好小明！5 門課不算少，要注意時間分配喔。
你：其中有一門是資料結構，好難
校園小助理： 資料結構確實是大一的關卡，建議多畫圖理解，並且每個資料結構都自己實作一次。
你：我剛剛說我修了幾門課？
校園小助理： 你說這學期修了 5 門課，其中一門是資料結構。
你：exit
校園小助理：掰掰，祝你有美好的一天！
```

注意第三個問題：模型記得「5 門課」和「資料結構」，因為它們都在 `chat_history` 裡。

> **小提醒**：在 Colab 裡，如果儲存格正在等你 `input()`，其他儲存格會無法執行。記得輸入 `exit` 結束，或按儲存格左邊的 ■ 停止按鈕。

### 程式 3-4：算算看，越聊越貴

這段**不需要 API key**。我們用簡單的假設，算出每一輪送出的 token 數和累積的總量：

```python
# 假設：system 訊息 50 個 token，每則使用者訊息和模型回答都是 50 個 token
SYSTEM_TOKENS = 50
MESSAGE_TOKENS = 50

total_input = 0  # 累積送出的輸入 token

print("輪數 | 這一輪送出的 token | 累積送出的 token")
print("-----+-------------------+-----------------")
for round_no in range(1, 11):
    # 第 n 輪送出：system + 前面 (n-1) 輪的一問一答 + 這一輪的問題
    messages_count = (round_no - 1) * 2 + 1
    this_round = SYSTEM_TOKENS + messages_count * MESSAGE_TOKENS
    total_input += this_round
    print(f"{round_no:>4} | {this_round:>17} | {total_input:>15}")
```

**逐段解說：**

- **`SYSTEM_TOKENS`、`MESSAGE_TOKENS`**：假設的數字，方便計算。真實情況每則訊息長短不同，但趨勢一樣。
- **`messages_count = (round_no - 1) * 2 + 1`**：第 n 輪時，前面已經有 n-1 輪的「一問一答」（每輪 2 則），再加上這一輪的問題（1 則）。
- **`this_round`**：這一輪實際送出的 token 數 = system ＋ 所有訊息。
- **`total_input += this_round`**：每一輪都要付費，所以要累加起來。
- **`f"{round_no:>4}"`**：`>4` 是 f-string 的格式設定，意思是「靠右對齊、佔 4 格寬」，讓表格整齊。

**預期輸出：**

```text
輪數 | 這一輪送出的 token | 累積送出的 token
-----+-------------------+-----------------
   1 |               100 |             100
   2 |               200 |             300
   3 |               300 |             600
   4 |               400 |            1000
   5 |               500 |            1500
   6 |               600 |            2100
   7 |               700 |            2800
   8 |               800 |            3600
   9 |               900 |            4500
  10 |              1000 |            5500
```

**觀察重點：**

- 每一輪送出的量是「直線」成長（100、200、300⋯⋯）。
- 但**累積的量**成長得更快：5 輪是 1500，10 輪是 5500，輪數變 2 倍，總量變成大約 3.7 倍；輪數越多，越接近 4 倍。
- 這還只是聊天。第 7 章的 Agent 每一步都會呼叫一次 LLM，一個問題可能就要呼叫好幾次，這個問題會更明顯。

### 程式 3-5：只送最近的對話（截斷）

這段的 `trim_history()` 本身**不需要 API key**，可以直接測試：

```python
def trim_history(chat_history, max_messages=6):
    """
    回傳一份「精簡版」的對話紀錄：保留 system 訊息 ＋ 最近 max_messages 則訊息。
    原本的 chat_history 不會被修改。
    """
    # 把 system 訊息和其他訊息分開
    system_messages = [m for m in chat_history if m["role"] == "system"]
    other_messages = [m for m in chat_history if m["role"] != "system"]

    # 只保留最後 max_messages 則
    recent = other_messages[-max_messages:]

    # 確保第一則是使用者說的話（不要從模型的回答開始，對話才合理）
    while recent and recent[0]["role"] != "user":
        recent = recent[1:]

    return system_messages + recent


# 測試：做一份有 5 輪對話的假紀錄
test_history = [{"role": "system", "content": "你是校園小助理。"}]
for i in range(1, 6):
    test_history.append({"role": "user", "content": f"問題 {i}"})
    test_history.append({"role": "assistant", "content": f"回答 {i}"})

trimmed = trim_history(test_history, max_messages=4)

print("原本有", len(test_history), "則；精簡後有", len(trimmed), "則")
for msg in trimmed:
    print(f"[{msg['role']}] {msg['content']}")
```

**逐段解說：**

- **分開 system 和其他訊息**：用 list comprehension（串列生成式，`[m for m in ... if ...]`，一行寫完的 for 迴圈）把 `system` 訊息挑出來，確保它一定會被保留。
- **`other_messages[-max_messages:]`**：負數索引代表「從後面數」，`[-4:]` 就是「最後 4 個」。
- **`while recent and recent[0]["role"] != "user"`**：如果切下來的第一則剛好是模型的回答（`assistant`），就把它去掉，讓對話從使用者的問題開始，模型比較不會搞混。
- **`return system_messages + recent`**：兩個 list 用 `+` 接起來，回傳一個**新的** list。原本的 `chat_history` 完全沒被改動，所以完整的紀錄還在。
- **測試的部分**：用迴圈造出 5 輪假對話（共 11 則），精簡成 system ＋ 最近 4 則。

**預期輸出：**

```text
原本有 11 則；精簡後有 5 則
[system] 你是校園小助理。
[user] 問題 4
[assistant] 回答 4
[user] 問題 5
[assistant] 回答 5
```

**怎麼用在聊天迴圈裡？** 只要把程式 3-3 裡的這一行：

```python
reply = call_llm(chat_history)
```

改成：

```python
reply = call_llm(trim_history(chat_history, max_messages=6))
```

這樣 `chat_history` 仍然保存**完整**的紀錄，但每次只把**精簡版**送給 LLM。存的和送的分開管理，是之後 Agent 程式也會沿用的觀念。

## 【常見錯誤】

| 錯誤情況 | 原因 | 解決方式 |
|---------|------|---------|
| 模型還是不記得前面說的話 | 只送了最新一句，而不是整份 `chat_history` | 確認呼叫的是 `call_llm(chat_history)` |
| 模型記得使用者的話，卻不記得自己的回答 | 忘了把模型的回答 `append` 回去 | 每一輪都要記得第 3 步：`append` assistant 訊息 |
| 同一句話在紀錄裡出現兩次 | 同一則訊息 `append` 了兩次 | 檢查每一輪是否剛好各 `append` 一次 user、一次 assistant |
| 截斷之後模型忘了自己的角色 | 截斷時把 system 訊息也刪掉了 | system 訊息要另外保留（參考 `trim_history()`） |
| 聊很久之後回應越來越慢、費用變高 | 每輪重送全部歷史，token 不斷累積 | 用 `trim_history()` 只送最近的對話 |
| Colab 其他儲存格都不能執行 | 聊天迴圈還在等 `input()` | 輸入 `exit`，或按 ■ 停止儲存格 |
| 把 `chat_history` 寫在 `chat()` 外面，結果每次聊天都接著上次的內容 | 全域變數沒有被重設 | 在 `chat()` 函式裡面建立 `chat_history` |

---

## 【本章小結】

1. LLM API 是**無狀態（stateless）**的：每次呼叫彼此獨立，模型只看得到「這一次」送過去的內容。
2. 「記憶」是程式做出來的：用 `chat_history` 保存對話，每一輪「append 使用者的話 → 送出整份紀錄 → append 模型的回答」。
3. `assistant` 角色用來記錄模型之前說過的話，讓模型知道對話的來龍去脈。
4. **上下文長度（context window）**是模型一次能讀的 token 上限；就算沒超過，太長也會變貴、變慢、品質下降。
5. 每一輪都重送全部歷史，累積費用會比對話輪數成長得快很多；常見的解法是只送 system ＋ 最近幾則訊息（截斷）。
