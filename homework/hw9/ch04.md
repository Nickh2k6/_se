# 第 4 章　控制輸出

## 【本章重點】

到目前為止，模型的回答都是「給人看的文字」，程式很難從中挑出需要的資料。這一章要讓模型**照規定的格式回答**，讓程式也讀得懂。
做法有兩步：先用 **system prompt** 規定模型的角色與規則，再要求它**只輸出 JSON**，然後用 `json.loads()` 把文字變成 Python dict。
模型偶爾會把格式弄錯，所以程式一定要能**清理、檢查、失敗時重試**。最後我們寫出 `mock_llm()`，讓沒有 API key 的讀者也能跑完後面所有章節。

---

## 【為什麼需要這一章】

第 3 章做出了會記得對話的聊天機器人。但假設使用者問：

```text
你：星期三有什麼課？
模型：星期三的話，我需要查一下你的課表才能告訴你喔！你可以提供你的課表嗎？
```

模型很有禮貌，但**你的程式**看到這句話，完全不知道該做什麼。如果你想讓程式「發現使用者要查星期三的課表，然後真的去查」，你得從這一大段中文裡找出：

- 使用者想做什麼？→ 查課表
- 查哪一天？→ 星期三

用 `if "課" in reply` 這種方法去猜，非常不可靠：模型每次措辭都不一樣，可能說「課程」、「上課」、「行程」⋯⋯

這一章要解決的問題是：**怎麼讓模型的回答，變成程式可以直接使用的資料？**

這也是通往「工具呼叫」的最後一塊拼圖：程式得先**讀懂**模型想做什麼，下一章才能**幫它去做**。

---

## 【觀念解說】

### 4.1 給人看的回答 vs 給程式看的回答

| | 給人看（自由文字） | 給程式看（結構化資料） |
|---|---|---|
| 範例 | 「星期三的話，我需要查一下你的課表⋯⋯」 | `{"intent": "schedule", "day": "星期三"}` |
| 優點 | 自然、親切 | 程式可以直接用 `result["day"]` 取值 |
| 缺點 | 程式要「猜」意思 | 人讀起來比較生硬 |

**結構化輸出（structured output）**：讓模型照固定的格式（例如 JSON）產生回答，讓程式可以準確地讀取每一個欄位。

**比喻：填表格 vs 寫作文。**

請同學「寫一段話介紹自己」，每個人寫法都不同，你要從作文裡找出他的學號，很辛苦。改成發一張**表格**：「姓名：＿＿　學號：＿＿　系級：＿＿」，每個人都照格子填，你一眼就能找到學號。

對 LLM 來說：**system prompt 就是發表格的人，JSON 就是那張表格。**

### 4.2 System prompt：設定角色與規則

**System prompt（系統提示詞）**：放在 `system` 角色裡的文字，用來告訴模型「你是誰、要遵守什麼規則、用什麼格式回答」。第 2 章介紹過 `system` 角色，這一章正式把它當成**控制模型的主要工具**。

**Prompt（提示詞）**：你送給模型的文字指令。寫 prompt 的技巧叫做**提示工程（prompt engineering）**。

一個好的 system prompt 通常包含：

```text
  ┌───────────────────────────────────────────────┐
  │ 1. 角色：你是誰、服務誰                          │  ← 決定語氣和立場
  │ 2. 規則：一定要做的、絕對不能做的                 │  ← 決定行為範圍
  │ 3. 格式：回答長什麼樣子（字數、語言、JSON⋯⋯）    │  ← 決定輸出形狀
  │ 4. 範例：給一兩個「標準答案」                     │  ← 最有效的教法
  └───────────────────────────────────────────────┘
```

本書把「角色＋規則」和「格式」**分開寫成兩個變數**：

- `SYSTEM_PROMPT`：校園小助理的**角色和規則**，全書都會用。
- `JSON_FORMAT_PROMPT`：本章用的**JSON 格式規定**。

需要時再用字串相加組合起來。這樣做的好處是：下一章要加「工具說明」時，只要再多寫一段接上去，不用把 `SYSTEM_PROMPT` 改得亂七八糟。

> **System prompt 不是萬能的。** 它是「強烈的建議」，不是「程式的強制規則」。模型大部分時候會遵守，但不保證 100%。所以程式端一定還要檢查（4.5 節），而重要的安全規則更不能只靠 prompt（第 9 章）。

### 4.3 要求輸出 JSON

要讓模型輸出 JSON，在 prompt 裡要講清楚三件事：

1. **只輸出 JSON**，不要有任何其他文字（模型很喜歡加「好的！以下是結果：」）。
2. **欄位有哪些**、每個欄位可以放什麼值。
3. **給一個範例**。範例比任何說明都有效。

本章使用的格式是判斷使用者的**意圖（intent）**，也就是「使用者想做什麼」：

```json
{"intent": "schedule", "day": "星期三", "reply": "我幫你查星期三的課表。"}
```

| 欄位 | 意思 | 可能的值 |
|------|------|---------|
| `intent` | 使用者想做什麼 | `"schedule"`（查課表）、`"weather"`（查天氣）、`"chat"`（閒聊） |
| `day` | 跟哪一天有關 | `"星期一"`～`"星期日"`，沒提到就是 `null` |
| `reply` | 要對使用者說的話 | 一句簡短的話 |

> **`null`** 是 JSON 的「空值」，轉成 Python 後會變成 `None`。

### 4.4 用 `json.loads()` 解析

模型回傳的永遠是**字串**（str），就算它長得像 JSON，在 Python 眼中也只是一串文字。要把它變成 dict，要用 Python 內建的 `json` 模組：

```text
  模型回傳的字串                         json.loads()           Python dict
  '{"intent": "schedule", "day": ...}'  ─────────────▶  {"intent": "schedule", "day": ...}
       type 是 str                                             type 是 dict
       不能用 ["intent"] 取值                                    可以用 ["intent"] 取值
```

- `json.loads(字串)`：JSON 文字 → Python 資料（**load s**tring，從字串載入）。
- `json.dumps(資料)`：Python 資料 → JSON 文字（**dump s**tring，倒出成字串）。第 2 章印出回應時用過。

### 4.5 格式錯誤怎麼辦

模型是用「文字接龍」產生 JSON 的，它不是真的在「寫程式」，所以偶爾會出錯。常見的狀況：

| 狀況 | 模型的回答長這樣 | `json.loads()` 結果 |
|------|-----------------|-------------------|
| 用 Markdown 標記包起來 | `` ```json\n{"intent": "chat"}\n``` `` | ❌ 失敗 |
| 前面多講一句話 | `好的！{"intent": "chat"}` | ❌ 失敗 |
| 少了結尾括號（被長度上限切斷） | `{"intent": "chat", "reply": "嗨` | ❌ 失敗 |
| 用單引號 | `{'intent': 'chat'}` | ❌ 失敗（JSON 規定只能用雙引號） |
| 正確 | `{"intent": "chat"}` | ✅ 成功 |

**處理的策略，由輕到重：**

```text
  模型回答
     │
     ▼
  ① 清理：只取第一個 { 到最後一個 } 之間的文字
     │       （去掉 ```json 標記、前後多餘的話）
     ▼
  ② 解析：try: json.loads()
     │
     ├── 成功 ──▶ 回傳 dict ✅
     │
     └── 失敗 ──▶ ③ 重試：把「你的格式錯了」告訴模型，請它重新回答
                      │
                      └── 重試幾次還是失敗 ──▶ 回傳 None，讓程式決定怎麼處理
```

第 ③ 步很重要：**把錯誤告訴模型，讓它自己修正**。這個觀念在第 8 章會再出現，而且會變成 Agent 可靠的關鍵。

另外，要求 JSON 時，建議把 `temperature` 設成 `0`。格式這種事情不需要創意，越穩定越好。

### 4.6 用 API 的 JSON 模式

靠 prompt 要求 JSON，終究只是「拜託」模型。Gemini API 提供一個更可靠的方式：在設定裡加上

```python
response_mime_type="application/json"
```

**MIME type（媒體類型）**：用來標示「這份資料是什麼格式」的標籤，例如 `text/plain`（純文字）、`application/json`（JSON）。

設定之後，Gemini 在產生回答時會**被限制只能產生合法的 JSON**，不會再有 `` ```json `` 標記或多餘的話。

| | 只靠 prompt | prompt ＋ JSON 模式 |
|---|---|---|
| 合法的 JSON 語法 | 大部分時候 | 保證 |
| 欄位名稱和內容正確 | 大部分時候 | 大部分時候（還是要靠 prompt 說清楚） |
| 換別家 API 能不能用 | 可以 | 要看那家有沒有類似功能 |

> 進一步還可以用 `response_schema` 參數，精確指定每個欄位的名稱和型別，讓模型連欄位都不會寫錯。本書為了保持簡單，只用 `response_mime_type`。

**JSON 模式保證的是「語法」，不是「內容」。** 模型還是可能把 `intent` 寫成 `"課表"` 而不是 `"schedule"`，所以程式端的檢查仍然不能省。

### 4.7 寫出 mock LLM

第 0 章提過，本書會提供一個**假的 LLM**。現在是時候寫它了，因為從下一章開始，所有程式都會依賴「模型輸出 JSON → 程式解析」這個流程，而這個流程用規則就能模擬。

`mock_llm()` 的設計原則：

1. **呼叫方式和 `call_llm()` 一模一樣**：吃同樣的 `messages`、同樣的參數，回傳同樣是字串。
2. **用關鍵字規則決定回答**：看最後一則使用者訊息有沒有「課」「天氣」之類的字。
3. **故意模擬真實模型的壞習慣**：不是 JSON 模式時，會把 JSON 用 `` ```json `` 包起來，讓你的清理程式有機會派上用場。

最後，我們用一個開關變數來決定「這次要用真的還是假的」：

```text
  USE_MOCK = False  ──▶  llm = call_llm   （真的 Gemini）
  USE_MOCK = True   ──▶  llm = mock_llm   （假的 LLM，不用 API key）

  從第 5 章開始，所有程式都呼叫 llm(messages)，不再直接寫 call_llm 或 mock_llm
```

在 Python 裡，**函式也是一種值**，可以存進變數裡。`llm = call_llm` 不是「呼叫」call_llm（沒有括號），而是讓 `llm` 這個名字指向 `call_llm` 這個函式。之後寫 `llm(messages)`，就等於寫 `call_llm(messages)`。

```python

import json
from google import genai
from google.genai import types
from google.colab import userdata

# 從 Colab 密鑰讀取 API key
api_key = userdata.get("GEMINI_API_KEY")

# 全書使用的模型名稱
MODEL_NAME = "gemini-3.5-flash-lite"

# 建立連線物件
client = genai.Client(api_key=api_key)


def call_llm(messages, temperature=None, max_output_tokens=1024):
    """
    把通用格式的 messages 送給 Gemini，回傳模型的文字回答。
    messages 的格式：[{"role": "system" / "user" / "assistant", "content": "文字"}, ...]
    """
    system_text = None
    contents = []

    # 把通用格式轉成 Gemini 的格式
    for msg in messages:
        if msg["role"] == "system":
            # system 不放進 contents，而是另外交給 system_instruction
            system_text = msg["content"]
        else:
            # Gemini 把 assistant 叫做 model
            role = "model" if msg["role"] == "assistant" else "user"
            contents.append({"role": role, "parts": [{"text": msg["content"]}]})

    response = client.models.generate_content(
        model=MODEL_NAME,
        contents=contents,
        config=types.GenerateContentConfig(
            system_instruction=system_text,
            temperature=temperature,
            max_output_tokens=max_output_tokens,
        ),
    )

    # 回答是空的時候 response.text 會是 None，統一轉成空字串比較好處理
    return response.text or ""


print("環境準備完成！")
```

### 程式 4-1：用 system prompt 設定角色與規則

```python
# 校園小助理的角色與規則（全書共用）
SYSTEM_PROMPT = """你是「金門大學校園小助理」，服務對象是金門大學的學生。

規則：
1. 一律使用繁體中文回答。
2. 回答簡短，最多三句話。
3. 不知道或不確定的事情，直接說「我不確定」，絕對不要編造。
4. 只回答和校園生活、課業有關的問題；其他問題請禮貌地拒絕。"""

questions = [
    "資工系的系主任是誰？",
    "幫我寫一首關於股票的詩。",
]

for q in questions:
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": q},
    ]
    print("你：", q)
    print("小助理：", call_llm(messages))
    print()
```

**逐段解說：**

- **`SYSTEM_PROMPT`**：用三個引號 `"""` 寫多行字串。內容照 4.2 節的結構：先寫**角色**，再條列**規則**。全大寫的名稱表示這是全書共用的設定。
- **規則 3**：「不知道就說不確定」是針對第 1 章的**幻覺**問題。它不能完全消除幻覺，但能明顯減少。
- **規則 4**：限制回答範圍，避免小助理被拿去做不相關的事。
- **for 迴圈**：每個問題都建立一份新的 `messages`（system ＋ user），看模型會不會遵守規則。

**預期輸出：**

```text
你： 資工系的系主任是誰？
小助理： 我不確定目前資工系系主任是哪一位，建議你到資工系網站或系辦查詢最新資訊。

你： 幫我寫一首關於股票的詩。
小助理： 抱歉，我只能協助校園生活和課業相關的問題。如果你有課程或校園方面的疑問，歡迎問我！
```

比較第 1 章程式 1-2：同樣是問系主任，有了規則 3，模型選擇承認不知道，而不是接龍出一個名字。

### 程式 4-2：要求模型輸出 JSON

```python
# JSON 格式的規定（本章使用）
JSON_FORMAT_PROMPT = """請判斷使用者想做什麼，並且「只輸出」一個 JSON 物件，不要輸出任何其他文字。

格式：
{"intent": "意圖", "day": "星期幾或 null", "reply": "給使用者的一句話"}

intent 只能是以下其中一個：
- "schedule"：查詢課表
- "weather"：查詢天氣
- "chat"：其他閒聊

範例：
使用者：星期三有什麼課？
輸出：{"intent": "schedule", "day": "星期三", "reply": "我幫你查星期三的課表。"}"""

messages = [
    # 把角色規則和 JSON 格式規定接在一起，當作 system prompt
    {"role": "system", "content": SYSTEM_PROMPT + "\n\n" + JSON_FORMAT_PROMPT},
    {"role": "user", "content": "星期五早上有課嗎？"},
]

reply = call_llm(messages, temperature=0)

print("模型的回答：", reply)
print("型別：", type(reply))
```

**逐段解說：**

- **`JSON_FORMAT_PROMPT`**：照 4.3 節的三個重點寫：「只輸出 JSON」、「欄位和可能的值」、「一個範例」。
- **`SYSTEM_PROMPT + "\n\n" + JSON_FORMAT_PROMPT`**：用字串相加把兩段組合起來，中間空一行（`\n\n`）讓模型容易區分段落。
- **`temperature=0`**：格式需要穩定，不需要創意。
- **`type(reply)`**：確認回傳的型別。

**預期輸出：**

```text
模型的回答： {"intent": "schedule", "day": "星期五", "reply": "我幫你查星期五的課表。"}
型別： <class 'str'>
```

注意型別是 `str`：雖然長得像 JSON，但它**還只是一串文字**。如果現在寫 `reply["intent"]`，會出現 `TypeError`。

### 程式 4-3：用 `json.loads()` 解析，讓程式「讀懂」

接在程式 4-2 後面執行：

```python
# 把 JSON 字串轉成 Python dict
result = json.loads(reply)

print("型別：", type(result))
print("意圖：", result["intent"])
print("哪一天：", result["day"])
print("回覆：", result["reply"])

# 程式根據意圖，決定下一步要做什麼
if result["intent"] == "schedule":
    print(f"\n→ 程式判斷：要去查「{result['day']}」的課表")
elif result["intent"] == "weather":
    print("\n→ 程式判斷：要去查天氣")
else:
    print("\n→ 程式判斷：一般閒聊，直接回覆就好")
```

**逐段解說：**

- **`json.loads(reply)`**：把字串解析成 dict。之後就能用 `result["intent"]` 取值。
- **if / elif / else**：**程式根據模型的判斷，決定下一步要做什麼。** 這是本章最重要的一刻：模型負責「理解使用者」，程式負責「決定行動」。

**預期輸出：**

```text
型別： <class 'dict'>
意圖： schedule
哪一天： 星期五
回覆： 我幫你查星期五的課表。

→ 程式判斷：要去查「星期五」的課表
```

> 看到了嗎？程式現在**知道**要去查星期五的課表了。只差一步：真的寫一個「查課表」的函式，並把查到的結果交還給模型。這一步就是第 5 章的**工具呼叫**。

### 程式 4-4：清理與防呆 —— `parse_json_reply()`

這段**不需要 API key**。我們寫一個函式，專門處理 4.5 節列出的各種格式錯誤：

```python
def parse_json_reply(text):
    """
    把模型的回答解析成 dict。
    會先去掉 ```json 標記和前後多餘的文字；解析失敗就回傳 None。
    """
    # 找出第一個 { 和最後一個 } 的位置
    start = text.find("{")
    end = text.rfind("}")

    # 找不到完整的大括號，代表一定不是 JSON 物件
    if start == -1 or end == -1 or end < start:
        return None

    # 只取 { ... } 這一段
    json_text = text[start:end + 1]

    try:
        return json.loads(json_text)
    except json.JSONDecodeError:
        return None


# 測試各種模型可能給出的回答
test_replies = [
    '{"intent": "chat", "day": null, "reply": "你好！"}',
    '```json\n{"intent": "schedule", "day": "星期三", "reply": "好的"}\n```',
    '好的！以下是結果：{"intent": "weather", "day": null, "reply": "我幫你查天氣"}',
    '{"intent": "chat", "reply": "這個回答被切斷了',
    "{'intent': 'chat', 'day': None}",
]

for t in test_replies:
    print("原始回答：", repr(t))
    print("解析結果：", parse_json_reply(t))
    print()
```

**逐段解說：**

- **`text.find("{")`**：從左邊找第一個 `{` 的位置，找不到會回傳 `-1`。
- **`text.rfind("}")`**：從**右邊**找第一個 `}` 的位置（`r` 代表 right）。
- **`text[start:end + 1]`**：切出 `{` 到 `}` 這一段。`end + 1` 是因為切片不包含結尾位置。這一步就把 `` ```json `` 標記和「好的！以下是結果：」這種多餘文字都去掉了。
- **`try` / `except json.JSONDecodeError`**：`json.loads()` 遇到不合法的 JSON 會丟出 `JSONDecodeError`。我們接住它，回傳 `None`，而不是讓整個程式當掉。
- **`repr(t)`**：印出字串的「原始樣子」，換行會顯示成 `\n`，方便看清楚內容。
- **測試資料**：五種情況分別對應 4.5 節表格的「正確」、「Markdown 標記」、「多講一句話」、「被切斷」、「單引號」。

**預期輸出：**

```text
原始回答： '{"intent": "chat", "day": null, "reply": "你好！"}'
解析結果： {'intent': 'chat', 'day': None, 'reply': '你好！'}

原始回答： '```json\n{"intent": "schedule", "day": "星期三", "reply": "好的"}\n```'
解析結果： {'intent': 'schedule', 'day': '星期三', 'reply': '好的'}

原始回答： '好的！以下是結果：{"intent": "weather", "day": null, "reply": "我幫你查天氣"}'
解析結果： {'intent': 'weather', 'day': None, 'reply': '我幫你查天氣'}

原始回答： '{"intent": "chat", "reply": "這個回答被切斷了'
解析結果： None

原始回答： "{'intent': 'chat', 'day': None}"
解析結果： None
```

前三種都救回來了；後兩種格式真的壞掉，安全地回傳 `None`，程式沒有當掉。注意 JSON 的 `null` 轉成 Python 後變成 `None`。

`parse_json_reply()` 在下一章會繼續使用，用來解析模型想呼叫的工具。

### 程式 4-5：解析失敗就重試 —— `ask_json()`

```python
def ask_json(messages, max_retries=2):
    """
    呼叫 LLM 並解析 JSON。
    如果格式錯誤，就把錯誤告訴模型，請它重新回答，最多重試 max_retries 次。
    """
    # 複製一份 messages，避免改到呼叫端原本的 list
    messages = list(messages)

    for attempt in range(max_retries + 1):
        reply = call_llm(messages, temperature=0)
        result = parse_json_reply(reply)

        if result is not None:
            return result

        # 解析失敗：把模型的錯誤回答和修正要求加進對話，再試一次
        print(f"[第 {attempt + 1} 次解析失敗] 模型回答：{reply}")
        messages.append({"role": "assistant", "content": reply})
        messages.append({
            "role": "user",
            "content": "你剛剛的回答不是正確的 JSON。請只輸出一個 JSON 物件，不要有任何其他文字。",
        })

    # 重試完還是失敗
    return None


messages = [
    {"role": "system", "content": SYSTEM_PROMPT + "\n\n" + JSON_FORMAT_PROMPT},
    {"role": "user", "content": "明天會下雨嗎？要不要帶傘？"},
]

result = ask_json(messages)
print("最終結果：", result)
```

**逐段解說：**

- **`messages = list(messages)`**：`list()` 會建立一個新的 list。如果不複製，後面的 `append` 會直接改到呼叫端傳進來的那個 list，造成意想不到的問題。
- **`for attempt in range(max_retries + 1)`**：第一次嘗試加上 `max_retries` 次重試，所以總共最多 3 次。
- **成功就馬上 `return`**：大部分情況第一次就成功，迴圈不會跑第二次。
- **失敗時的兩個 `append`**：
  - 先把模型**錯誤的回答**以 `assistant` 身分加進去，讓模型知道「自己剛剛說了什麼」。
  - 再以 `user` 身分告訴它「格式錯了，請修正」。
  - 這就是第 3 章學到的「對話記憶」的應用：模型看得到自己的錯誤，才知道要怎麼改。
- **全部失敗就回傳 `None`**：讓呼叫端自己決定要怎麼處理（例如告訴使用者「我現在無法處理」）。

**預期輸出（大部分情況第一次就成功）：**

```text
最終結果： {'intent': 'weather', 'day': None, 'reply': '我幫你查一下明天的天氣。'}
```

如果真的遇到格式錯誤，你會看到類似這樣的輸出：

```text
[第 1 次解析失敗] 模型回答：明天的天氣我需要查一下喔！
最終結果： {'intent': 'weather', 'day': None, 'reply': '我幫你查一下明天的天氣。'}
```

> 注意 `day` 是 `None`：使用者說的是「明天」，但模型**不知道今天星期幾**（第 1 章：模型沒有時鐘），所以填不出星期幾。這個問題要等第 5 章的 `get_current_time()` 工具來解決。

### 程式 4-6：升級 `call_llm()`，加入 JSON 模式

我們幫 `call_llm()` 加一個參數 `json_mode`。**預設是 `False`**，所以之前寫的程式完全不受影響。

```python
def call_llm(messages, temperature=None, max_output_tokens=1024, json_mode=False):
    """
    把通用格式的 messages 送給 Gemini，回傳模型的文字回答。
    messages 的格式：[{"role": "system" / "user" / "assistant", "content": "文字"}, ...]
    json_mode=True 時，要求 Gemini 一定要輸出合法的 JSON。
    """
    system_text = None
    contents = []

    # 把通用格式轉成 Gemini 的格式
    for msg in messages:
        if msg["role"] == "system":
            system_text = msg["content"]
        else:
            role = "model" if msg["role"] == "assistant" else "user"
            contents.append({"role": role, "parts": [{"text": msg["content"]}]})

    response = client.models.generate_content(
        model=MODEL_NAME,
        contents=contents,
        config=types.GenerateContentConfig(
            system_instruction=system_text,
            temperature=temperature,
            max_output_tokens=max_output_tokens,
            # JSON 模式：限制模型只能輸出 JSON；不是 JSON 模式就不設定（None）
            response_mime_type="application/json" if json_mode else None,
        ),
    )

    return response.text or ""


# 測試：開啟 JSON 模式
messages = [
    {"role": "system", "content": SYSTEM_PROMPT + "\n\n" + JSON_FORMAT_PROMPT},
    {"role": "user", "content": "嗨，你今天好嗎？"},
]
reply = call_llm(messages, temperature=0, json_mode=True)
print("模型的回答：", reply)
print("解析結果：", json.loads(reply))
```

**逐段解說：**

- **新參數 `json_mode=False`**：放在最後面，而且有預設值，這樣舊的呼叫方式 `call_llm(messages)` 仍然可以正常使用。這是修改共用函式時很重要的原則：**不要破壞原本的用法**。
- **`response_mime_type="application/json" if json_mode else None`**：這是 Python 的**條件運算式**（一行的 if-else）。`json_mode` 為 `True` 時設成 `"application/json"`，否則設成 `None`（等於不設定）。
- **其他部分**：和原本的 `call_llm()` 完全一樣。
- **測試**：開了 JSON 模式之後，回答保證是合法 JSON，可以直接 `json.loads()`。不過還是建議用 `parse_json_reply()` 比較保險，因為內容（例如 `intent` 的值）還是有可能不符合規定。

**預期輸出：**

```text
模型的回答： {"intent": "chat", "day": null, "reply": "我很好，謝謝關心！有什麼校園問題需要幫忙嗎？"}
解析結果： {'intent': 'chat', 'day': None, 'reply': '我很好，謝謝關心！有什麼校園問題需要幫忙嗎？'}
```

> **之後的章節都使用這個升級版的 `call_llm()`。**

### 程式 4-7：假的 LLM —— `mock_llm()` 與 `llm` 開關

這段**不需要 API key**。

```python
WEEKDAYS = ["星期一", "星期二", "星期三", "星期四", "星期五", "星期六", "星期日"]


def mock_llm(messages, temperature=None, max_output_tokens=1024, json_mode=False):
    """
    假的 LLM：用簡單的關鍵字規則模擬回答。
    呼叫方式和 call_llm() 完全一樣，回傳的也是字串。
    """
    # 找出最後一則使用者訊息
    last_user = ""
    for msg in reversed(messages):
        if msg["role"] == "user":
            last_user = msg["content"]
            break

    # 把所有 system 訊息接起來，看看有沒有要求 JSON
    system_text = " ".join(m["content"] for m in messages if m["role"] == "system")
    wants_json = json_mode or "JSON" in system_text

    # ===== 情況一：要求輸出 JSON =====
    if wants_json:
        # 從使用者的話裡找「星期幾」
        day = None
        for d in WEEKDAYS:
            if d in last_user:
                day = d
                break

        # 用關鍵字判斷意圖
        if "課" in last_user:
            result = {"intent": "schedule", "day": day, "reply": "我幫你查課表。"}
        elif "天氣" in last_user or "雨" in last_user:
            result = {"intent": "weather", "day": day, "reply": "我幫你查天氣。"}
        else:
            result = {"intent": "chat", "day": day, "reply": "（mock）你好，我是假的小助理！"}

        text = json.dumps(result, ensure_ascii=False)

        # 模擬真實模型的壞習慣：沒開 JSON 模式時，用 ```json 把答案包起來
        if not json_mode:
            text = "```json\n" + text + "\n```"
        return text

    # ===== 情況二：一般文字回答 =====
    if "你好" in last_user or "你是誰" in last_user:
        return "（mock）你好！我是假的校園小助理，只會用規則回答問題。"
    return f"（mock）我收到你的訊息了：「{last_user}」"


# ===== 開關：沒有 API key 就把 USE_MOCK 改成 True =====
USE_MOCK = False
llm = mock_llm if USE_MOCK else call_llm


# 測試 mock_llm（不管開關怎麼設，這裡都直接測假的）
messages = [
    {"role": "system", "content": SYSTEM_PROMPT + "\n\n" + JSON_FORMAT_PROMPT},
    {"role": "user", "content": "星期三有什麼課？"},
]
raw = mock_llm(messages)
print("mock 的原始回答：", repr(raw))
print("parse_json_reply：", parse_json_reply(raw))
print()
print(mock_llm([{"role": "user", "content": "你好"}]))
print()
print("目前 llm 指向：", llm.__name__)
```

**逐段解說：**

- **`WEEKDAYS`**：星期一到星期日的 list，用來從使用者的話裡找出是哪一天。
- **函式參數**：和升級版 `call_llm()` **一字不差**（`messages, temperature=None, max_output_tokens=1024, json_mode=False`）。`temperature`、`max_output_tokens` 在 mock 裡沒有作用，但一定要有，這樣任何呼叫 `call_llm()` 的程式都能直接換成 `mock_llm()`。
- **找最後一則使用者訊息**：`reversed(messages)` 從最後面往前看，找到第一個 `user` 就停（`break`）。
- **`wants_json`**：如果開了 `json_mode`，或 system prompt 裡有「JSON」這個字，就當作要輸出 JSON。
- **情況一（JSON）**：
  - 用 for 迴圈檢查使用者的話裡有沒有「星期X」。
  - 用 `in` 檢查關鍵字，決定 `intent`。
  - `json.dumps(..., ensure_ascii=False)` 把 dict 轉成 JSON 字串，中文保持原樣。
  - 沒開 JSON 模式時，故意加上 `` ```json `` 標記，模擬真實模型的壞習慣。
- **情況二（一般文字）**：簡單的關鍵字回答。開頭的「（mock）」讓你一眼看出這是假的回答。
- **`USE_MOCK` 與 `llm`**：
  - `llm = mock_llm if USE_MOCK else call_llm`：根據開關，讓 `llm` 指向其中一個函式。注意兩個函式名稱後面**都沒有括號**，因為我們是要「函式本身」，不是要呼叫它。
  - `llm.__name__`：每個函式都有 `__name__` 屬性，記錄它的名字，用來確認 `llm` 現在指向哪一個。

**預期輸出：**

```text

```

可以看到：mock 的回答被 `` ```json `` 包起來了，但 `parse_json_reply()` 一樣能正確解析。

**mock_llm 和真的 LLM 差在哪？**

```text
  真的 LLM：  理解任何說法 —— 「禮拜三」「週三」「後天」都可能聽得懂
  mock_llm：  只認得寫好的關鍵字 —— 一定要出現「星期三」和「課」
```

mock_llm 一點都不聰明，但它**輸入和輸出的格式跟真的一模一樣**。所以用它來測試「程式的流程」完全沒問題，而且不花錢、不用網路、每次結果都相同，很適合除錯。

> **從第 5 章開始，所有程式都呼叫 `llm(...)`**，而不是直接寫 `call_llm(...)`。有 API key 的讀者保持 `USE_MOCK = False`；沒有的讀者改成 `True`。後面的章節會繼續幫 `mock_llm()` 加上新的規則（例如工具呼叫）。

## 【常見錯誤】

| 錯誤情況 | 原因 | 解決方式 |
|---------|------|---------|
| `TypeError: string indices must be integers` | 對字串用 `reply["intent"]`，忘了先 `json.loads()` | 先解析成 dict 再取值 |
| `json.decoder.JSONDecodeError` | 模型回答有 `` ```json `` 標記、多餘文字，或被切斷 | 用 `parse_json_reply()` 清理，失敗時重試 |
| `KeyError: 'day'` | 模型漏了某個欄位 | 用 `result.get("day")` 取值，或檢查欄位是否齊全（練習 4-2） |
| `intent` 出現 `"課表"`、`"查課"` 等意料外的值 | 模型沒照規定的選項回答 | prompt 寫清楚「只能是以下其中一個」，程式端也要檢查 |
| 回答出現「好的！以下是結果：」 | prompt 沒強調「只輸出 JSON」 | 在 prompt 中明確寫「不要輸出任何其他文字」，或開啟 JSON 模式 |
| JSON 被切斷 | `max_output_tokens` 太小 | 調大上限，並檢查第 2 章學過的停止原因 |
| 改了 `USE_MOCK` 卻沒有效果 | 改完開關沒有重新執行 `llm = ...` 那一行 | 改完後重跑整個程式 4-7 |
| 寫成 `llm = call_llm()` | 多了括號，變成「呼叫」函式並把回傳值存進去 | 改成 `llm = call_llm`（沒有括號） |

## 【本章小結】

1. **System prompt** 用來設定模型的角色、規則和格式；本書把角色規則（`SYSTEM_PROMPT`）和格式規定（`JSON_FORMAT_PROMPT`）分開寫，需要時再組合。
2. **結構化輸出**讓模型照 JSON 格式回答；程式用 `json.loads()` 把字串變成 dict，就能「讀懂」模型的判斷，並決定下一步行動。
3. 模型產生的 JSON 可能有格式錯誤：先清理（`parse_json_reply()`），失敗時把錯誤告訴模型並重試（`ask_json()`）。
4. Gemini 的 **JSON 模式**（`response_mime_type="application/json"`）保證語法正確，但內容仍要檢查。
5. `mock_llm()` 和 `call_llm()` 的呼叫方式完全一樣；從下一章起，所有程式都透過 `llm` 開關呼叫，沒有 API key 也能跑。
